# Build a replication

The replication of the bug must be as faithful as possible. Spend almost all of your effort here. Refuse to give up. Iterate aggressively.

It is insufficient to simply show that an error is triggered. Forcing a try/catch artificially is not helpful.
<bad_example>
Bug report: system timeout with an error message: "This system timed out."
Agent: I will mock the system to force it to time out. This shows me the same error message.
</bad_example>
The above fails as a replica because it does not get into the cause of the error.

Replicas include:
- a failing test. These are the best and rarest, because the developer should have caught the bug if the test is failing.
- curl or script against a dev server. Spin up as much dev architecture as possible to mimic, and then drive that architecture to replicate.
- replay a trace. Save a real log, and then replay it through the code.
- throwaway harness. Create a minimal subset of the system to identify the bug through simplicity. Rarely works first time; may require multiple harnesses to evaluate hypotheses.
- Fuzzing. If the issue is deterministic, run through 1000 random inputs (in code, not generated by llm) and hunt for it.
- Bisection. If the bug appeared between two known states, automate the process of 'boot at state, check, repeat' with git bisect run.

Once you have a replica, improve it until you can root cause.

- Can I make it faster? (Cache setup, skip unrelated init, narrow the test scope.)
- Can I make the signal sharper? (Assert on the specific symptom, not "didn't crash".)
- Can I make it more deterministic? (Pin time, seed RNG, isolate filesystem, freeze network.)

Non-deterministic bugs should have replicas that can be tested multiple times to try and 'catch' the bug 'in the wild'. Once you have a replica, make it more likely to trigger the non-deterministc bug. A 50%-flake bug is debuggable; 1% is not — keep raising the rate until it's debuggable.

# Reproduce and minimise

Confirm the loop reproduces the failure I described — not a lookalike nearby — across runs, and capture the exact symptom. Then strip inputs, callers, config, and steps one at a time until every remaining piece is load-bearing; removing any one turns the loop green.

# Hypothesise

Rank several before testing any; a single guess anchors you on the first idea. Make each one falsifiable by naming the change that would kill the bug and the change that would worsen it, keeping only the guesses that carry such a prediction. Show me the ranking first — I often re-rank it instantly — but proceed alone if I am away.

# Instrument

One probe per hypothesis, one variable at a time. Prefer a debugger breakpoint over logs; when you log, hit only the boundaries that separate hypotheses and tag each line `[DEBUG-a4f2]` so cleanup is one grep. Perf regressions are the exception — logs mislead, so measure a baseline (profiler, `performance.now()`, query plan), then bisect.
